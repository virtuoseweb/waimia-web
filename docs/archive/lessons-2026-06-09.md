## Flotte de pages service : injecter les CAPS DE SCHÉMA dans le brief worker dès le départ (2026-06-22)

- **Contexte** : flotte de 9 pages service money (V7-SVC, strategy/11 §16) produite par vagues de workers Opus (3//, plafond RAM), chacune écrivant un `.mdx` de 18 sections. Build + GF-1 centralisés par l'orchestrateur (jamais 2 builds //).
- **Défauts worker récurrents (build cassé `InvalidContentEntryDataError`)** captés au build central de la Vague 1, AVANT que la suite ne les répète :
  1. `related-cards-band` avec **5 cartes** alors que le schéma plafonne `cards` à **3** (`Too big: expected array to have <=3 items`).
  2. `description_fr`/`en` à **188-205 caractères** alors que le schéma plafonne à **180** (`Too big: expected string to have <=180 characters`).
- **Cause** : le brief commun ne listait PAS les caps de schéma des composants ; les workers ont rempli généreusement le maillage/SEO sans connaître les bornes.
- **Règle capitalisée** : un brief de page composable DOIT lister les **caps de schéma par type de section** (related-cards-band ≤3, problems-grid 3, case-card-grid ≤3, deliverables-grid ≤6, bento-grid ≤5) **et** les caps de frontmatter (`description` ≤175 strict pour marge sous 180), avec l'instruction « dans le doute, recopie le NOMBRE exact d'items depuis le canon ». Source de vérité des caps = `src/schemas/sections.ts` + le fichier canon (`consultant-claude.mdx`).
- **Méthode anti-récidive** : (A) durcir le brief APRÈS la 1ʳᵉ vague (fait : caps + description ajoutés → vagues 2-3 ont build vert du 1er coup). (B) AVANT le build central, lancer un pré-check déterministe sur chaque `.mdx` produit : nb sections, RCBmax (`awk`), longueurs description (`node`), 0 em-dash, maillage 100% green-list. Corriger en local (trim) ou renvoyer au worker selon l'ampleur. (C) Maillage : fournir au worker une **green-list d'URLs vérifiées dans `dist/`** (0 lien mort, 0 page noindex) ; un slot §16 sans cible réelle = OMIS, jamais inventé.

## Gutter site-wide : gate statique ≠ alignement réel + artefact reveal (2026-06-15)

- **Contexte** : harmonisation du gutter horizontal (décision Simon « gutter cohérent partout, heros centrés OK »). Gate `scripts/check-gutter.mjs` créé (FAIL si `.wrap*` avec padding horizontal ≠ `var(--gut)` ou token fantôme `var(--space-page-x)`).
- **Limite du gate statique** : il valide la VALEUR du gutter (padding token), pas l'ALIGNEMENT réel du contenu. Deux classes de bug lui échappent : (a) **double-gutter** = un `<section>` porte son propre `padding-inline` ET contient un `.wrap*` enfant → contenu à 64 au lieu de 32 (le gate ne scanne que les sélecteurs `.wrap*`, pas le padding du parent `section`) ; (b) **conteneur centré plus étroit** = `.wrap-wide` avec `max-width` réduit + `margin-inline:auto` → contenu décalé (145) sans override de padding. Les deux n'ont été vus que par la mesure runtime Playwright (`getBoundingClientRect().left + paddingLeft` par section).
- **Correctif appliqué** : double-gutter → zéro le `padding-inline` de la `<section>` (le `.wrap*` enfant reste le seul gutter) ; centré-étroit → déplacer le cap `max-width` du conteneur de page vers le sous-élément réel (ex. `.problems-grid__cards`) en left-aligné.
- **Artefact reveal (m'a touché 2×)** : les animations de reveal (`scale-in`, `reveal-*`) appliquent un `transform` non neutralisé tant que l'élément est hors viewport → `getBoundingClientRect()` faussé (ex. `book-session` mesuré à 61, réel 32 après scroll). **Méthode robuste GF-1 alignement** : scroller l'élément dans le viewport + attendre la fin de l'anim avant de mesurer la POSITION, OU mesurer le CSS (`paddingLeft`/`maxWidth`) immunisé contre le transform. Un gate d'alignement runtime doit forcer le reveal avant mesure.
- **À faire (task #4 e2e)** : ajouter un check runtime d'alignement (mesure contentLeft par section, assert sections de contenu == `--gut`, heros autorisés centrés) → seul vrai enforceur de « partout pareil », le gate statique ne suffit pas.

## Collision workers parallèles — git destructif + re-délégation (2026-06-10)

**Principe (renforce rule 60 + « 100% DS-driven »)** : tout composant **catalogué** porte son style dans un `<style>`/global.css **par classes**, 100% `var(--token)`. 0 attribut `style=` inline (sauf `data-*` d'état, ex. `data-tone`). 0 littéral px/em : réutiliser un token DS existant (jamais en créer) ; si aucun token n'a la bonne taille, `calc()` sur un token est toléré. Modèle de référence déjà propre dans le repo : `Breadcrumb.astro` (classes + `var(--text-small)`/`var(--tracking-mono-tight)`).
**Validation** : `grep -n "style=" <composant>.astro` ne doit montrer que des `data-*`. Un changement de token dans DS Studio doit se propager visuellement (GF-1).
**Corollaire taille** : un breadcrumb est un **signal d'orientation discret, jamais un héros** → token le plus petit (`--text-micro` 9px), 1 seule ligne garantie (nowrap + ellipsis sur le crumb courant), mobile dépouillé (crumbs + locale courte « FR » collée à droite, gap franc `--space-6`). S'il wrappe en 2 lignes sur mobile, il densifie le haut de page et paraît « non maîtrisé ».

## 2026-06-21 — Patterns catalogue (vague audit nuit)

### `set:html` obligatoire pour tout contenu texte pouvant porter du markup inline
Un titre/texte démo contenant `<i>…</i>` (accent typo) rendu via `{data.h2}` s'affiche **littéralement** (`<i>` visible) car Astro échappe le HTML par défaut. Tous les h2/h3 de section qui peuvent recevoir des balises (accents italique terracotta) DOIVENT utiliser `set:html={…}`. Bug réel : `FeatureGrid.astro:110` (commitments-grid) — un seul h2 oublié alors que les autres du fichier l'avaient. **Réflexe migration templates** : auditer chaque slot texte → si le contenu démo/réel contient `<i>`/`<br>`/`<strong>`, c'est `set:html`.

### Colonnes grid tolérantes au contenu : `minmax(min, max-content)` > largeur fixe
Une colonne grid fixe calibrée pour un contenu court casse dès que le contenu démo est plus long. Bug réel : `UseCaseIndex.astro:66` `grid-template-columns: 70px …` → préfixe « USE CASE 05 » (~11 ch mono) débordait sous le titre. Fix : `minmax(120px, max-content) …`. **Principe** : un composant catalogué doit survivre à sa propre démo (le contenu n'est pas garanti court).

### Le vide vertical en preview ≠ bug composant (dropcap)
Un float (dropcap) surdimensionné laisse un grand vide quand le contenu démo qui l'habille est court (3 lignes). En usage réel (paragraphe d'article long), le wrap est correct. **Ne pas "corriger" le CSS d'un composant pour un artefact de contenu démo court** — corriger le contenu démo (allonger le lead) ou accepter la limite preview. Jugement visuel GF-3 indispensable pour distinguer bug composant vs artefact démo.

### Vérification apostrophes FR : grep aussi spécifique que le fix (anti-faux-positif)
Sweep apostrophes FR dans section-demos.ts : « d agents », « d anomalies », « l orchestration » sont des **faux positifs EN** (« and agents », « and anomalies », « central orchestration »). La grep de vérif doit cibler le contexte FR exact, pas une sous-chaîne générique.

## Pattern: `set:html="..."` en ATTRIBUT CHAÎNE échappe les tags HTML (2026-06-21)
`/equipe/simon-beros` affichait `<i>nouvelle façon de travailler.</i>` en TEXTE LITTÉRAL. Astro échappe alors les tags (`<i>`→`&lt;i&gt;`) tout en laissant passer les entités (`&rsquo;`/`&nbsp;`). Fix = `<Fragment>...<i>...</i>...</Fragment>` (vrai élément JSX, 2 lignes). Leçon : pour injecter du HTML avec balises, utiliser la forme EXPRESSION `set:html={"..."}` OU du vrai JSX, jamais l'attribut chaîne littérale. Détecté au GF-3 visuel (le `<i>` littéral saute aux yeux) + confirmé HTML buildé, pas au build.
